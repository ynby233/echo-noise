## 4. 总体接口和状态约定

### 4.1 系统分工

```text
GitHub Actions → GHCR 两渠道 + 发布元数据
                          ↓
站长浏览器 → 应用更新协调服务 → 可选的带认证唤醒 → Dagu 固定任务
                   │                                  │
             持久化任务/偏好 ← 领取/回报 ← 容器内项目执行器
                                              │
                               持久记录/锁/固定部署配置
                                              ↓
                                  下载 → 停旧服务 → 备份 → 替换 → 核验
                                              ↓
                                  新服务接受结果回报，页面恢复
Dagu 内置定时调度 → 检查能力/补偿漏通知/按记录恢复（同一执行器与锁）
```

仍只有一条 API 任务通道，任务以应用数据库为准。唤醒只加速领取，不传另一套安装指令；Dagu 的排队/运行成功不等于应用更新成功。前期共享文件请求模式不作为第二套协议，持久状态文件只用于恢复与排障。

### 4.2 最小 API（名字可随现有路由风格微调，职责不变）

| 操作 | 权限/语义 |
| --- | --- |
| `GET /api/updates` | 按现有查看权限返回能力、已装显示信息、两个渠道；敏感完整构建信息仍按原有隐私边界。 |
| `PUT /api/updates/channel` | 站长修改后续跟随偏好；不产生安装任务。 |
| `POST /api/updates/tasks` | 生产已接通：站长选择 server-resolved 目标并返回任务 ID；近期能力不满足返回 412，目标变化返回 409。U6 唤醒在持久化成功后进行。 |
| `POST /api/updates/executor/check` | 专用执行器凭据上报实际部署/备份检查；当前有效窗口为 3 分钟，不以 Webhook 接收成功替代检查。 |
| `GET /api/updates/tasks/:id` | 授权查看进度和脱敏结果；不创建任务、不执行安装。 |
| `POST /api/updates/executor/claim` | 专用执行器凭据；原子领取最多一个本实例待执行任务，无任务 204。 |
| `POST /api/updates/executor/tasks/:id/events` | 当前任务对应执行器回报进度/结果；验证归属和状态转换，不可替他人任务报成功。 |
| `GET /api/updates/executor/runtime` | 专用凭据读取本实例完整构建身份，用于核实新进程；不复用用户登录 cookie。 |

初次配置需站长创建/撤销执行器凭据及显示连接状态；具体复用现有 token 工具先查代码。凭据只授予领取、回报和运行身份读取，不授予任意笔记读写、备份下载或用户管理。服务器只存不可逆验证值、展示一次；这是认证凭据存储要求，不是新增内容 hash 门禁。轮换不破坏已运行任务的本地完成/排障证据。

首次配对由站长和宿主管理员确认同一实例，执行器不得凭 token 自动信任任意新实例。接口不接收 shell、宿主路径、Compose 文件内容或任意镜像仓库。执行器固定配置决定更新什么，领取结果只包含验证过的目标产物。网络非本机时使用 HTTPS，禁止自动关闭证书校验；不使用日常账号密码/管理员 JWT 当执行器长期凭据。

已有数据库足以保存单实例任务与渠道偏好，不上 Redis、消息队列或事件框架。任务创建与 claim 采用事务/唯一性控制；具体数据库兼容策略沿用项目现状。最多一条未结束任务。普通 ID、事务、宿主 flock 和状态判断足够，不新增 baseline/冻结 contract/自定义校验协议。

**能力判断（U4/U5 已实现）：**“有凭据、曾经连过”不等于现在能安装。生产要求近期实际检查、同一登记实例、`u5-1` 执行器、Linux amd64/SQLite 及已验证数据保护。当前 `ExecutorCheckWindow` 为 3 分钟，Dagu 空闲时先按每分钟运行实际检查/领取，U6 根据实测耗时校准；不因只改调度工具放宽窗口或伪报 OK。若代码适配确需升级执行器版本，同步服务端兼容判断及测试。检查过期不重新分配已领取任务，也不建设额外心跳服务。

执行器脚本也是管理员安装的软件。初次安装后，兼容协议的应用更新可以继续使用原脚本；需要新备份能力或脚本变更时，明确提示一次性升级引导版本/脚本并暂时禁止安装。用普通版本/必要能力说明兼容性，不新增冻结协议或 hash 门禁，不承诺一次配置后永久无需维护，也不让网页自动下载执行任意 root 脚本。

### 4.3 任务状态与停机恢复

U2 已实现正常状态链：`pending → claimed → downloading → stopping → backing_up → replacing → verifying → succeeded`；失败记录 `failed`，结果不明使用 `needs_attention`。U3 直接对接现有状态转换，不自行重命名或跳过阶段；特殊恢复按实际合法转换处理，阶段与失败语义必须真实。

宿主在停止旧服务前落盘：任务 ID、已选择 digest、旧镜像 ID/digest、固定配置位置、当前阶段、备份位置。文件原子写入、管理员权限、内容脱敏。应用下线期间事件先保存在本地，恢复后重试回报同一任务；事件重复不能重复安装，回报顺序不能倒退。

不要把心跳超时直接解释为可以重新领取：旧执行器可能仍在备份/替换。任务 claim 后不自动重新分配；宿主重启或超时先根据本地记录、实际容器、镜像和健康核对，再继续可安全重试步骤或标记人工处理。claim 成功但响应丢失时同一执行器应能取回原任务，不能生成第二个任务。进度断线只影响展示，不影响执行。

服务迟迟起不来时，Echo Noise 网页没有后台可查询是正常限制；保留独立 Dagu 日志和执行器记录并提供查阅指引。NAS/Docker 整体离线时 Dagu 网页也不可用，需恢复后读持久日志，不能承诺故障页面一直在线。

### 4.3.1 回报与本地恢复的具体顺序

1. 本地分别记录服务端已确认阶段、宿主实际完成步骤、尚未确认的事件；每个可能改变容器/数据的动作前先写执行意图，完成后写结果。记录保留到结果确认，不能服务一停止就只靠内存。
2. 应用停机期间，继续已核定的宿主操作，按顺序保存待回报事件。恢复后串行补报；请求超时重发同一事件，不直接跳到 succeeded，也不反向回报历史阶段覆盖当前状态。
3. 服务端响应 409 或本地/服务端不一致时，先核对该任务与真实容器；不能用忽略错误、创建新任务或重复替换“修复”。U2 仅允许合法状态转换及当前阶段的幂等重复，不是任意历史事件都接受。
4. 重启后先处理已有本地记录，再领取任务。同一执行器的 claim 可以取回仍归属自己的活动任务；若与本地任务不一致或 instance_id 改变，停止并留证。已结束任务使用自己最终事件补报确认；正常轮换后的旧凭据不应因此被要求还能调用 claim/runtime。
5. 密钥轮换、显式撤销、过期分别处理：正常轮换按 U2 允许范围继续当前任务；撤销/过期不会被本地记录绕过。记录只存凭据引用，不存明文 token；保留任务使用的受限凭据文件直到结案后再清理。

这里需要少量状态文件和普通 HTTP 重试，不需要另造通用队列。安装结果已确认前的回报失败只能触发补报；已经启动目标进程的事实不因回报失败消失。Dagu 停止/超时杀进程、执行容器重建、NAS 重启及 claim 响应丢失均按同一持久记录核对。

### 4.3.2 needs_attention 的人工结案（U4 交付，U5 展示）

此状态继续占用活动任务位置，不能按钮再点一次就创建另一安装。管理员先按任务 ID 查看宿主记录、新旧容器/镜像、备份和当前数据库状态：目标健康且身份正确则沿合法 verifying 路径复核完成；已明确停止操作则按合法失败路径结案；不能判断数据是否迁移/写入时先保留证据并人工恢复，禁止自动还原旧库。

常规优先使用当前任务所属执行器和现有接口。若凭据已被撤销、过期或本地记录丢失，U4 要交付明确的受权结案入口：优先最小宿主 CLI；确需后台接口时仅固定 ID 1 可针对指定任务结案，并记录理由/审计。先用此真实失败场景验证必要性，不加万能“清空更新状态”接口。不得重新签发 token 冒认原执行器、直接改库删任务、恢复旧业务库来解除占位，或绕过撤销规则。U5 提供操作指引，不提供自动数据库回退按钮。

### 4.4 渠道、版本和安全更新判断

展示版本、跟随渠道、实际已安装提交、目标 digest 分开保存。SHA 不按字符串大小排序；发布时间不证明代码更新。初期只支持同一 main 历史链上的自动更新：目标 revision 等于当前或是当前后代才允许；目标是祖先则保持当前、等待渠道追上；分叉或缺少可靠身份时拒绝自动判断。

正式 vX.Y.Z 由 Release 映射到实际提交，不只按标签日期比较。GitHub annotated tag 需解引用。已安装旧版只提供短 SHA 时只能在首次引导核对后补全，不能猜当前身份。API 限流/网络失败显示检查失败或带时间的缓存结果，不能当“已最新”。

同提交、同构建产物仅切渠道不强制安装。重建同一提交产生不同 digest 不能自动按“新 digest 就更好”处理，默认报告同源重建，若无明确发行修复策略不自动升级。正式/测试身份规则不要求把每次提交伪装成正式版本。

数据不兼容升级需显式迁移说明；“后代提交”只说明代码顺序，不自动证明迁移安全，升级失败保护仍必需。首期不提供自动降级按钮或自动数据库还原。

## 6. U1：渠道发布与版本发现

1. 阅读工作流、Dockerfile、构建身份、现有 Release/Tag/镜像状态；记录旧版行为和自动安装不可用状态，不触发真实发布。
2. 将自动测试构建接入 main push，保留 workflow_dispatch。路径过滤应包含 web、Go 模块/源码、公共资源、依赖锁、Dockerfile、构建/打包脚本及工作流自身；仅明确无产物影响的文档变更跳过。提供手动补建，不以扩大过滤省构建造成漏镜像。
3. 正式工作流限定 published 且非 prerelease/draft 的 Release；从该 Release 的确定提交构建，不误用触发时 main HEAD。正式版本首次发布先校验版本格式和提交归属；正式标签不悄悄覆盖已有不同内容。
4. 在既有 final-mcp 构建中写入完整 revision、构建时间和显示版本。保留现有 ID 1 才能看敏感标记的边界；执行器另走受限运行身份接口。
5. 先构建具体产物并 smoke，再移动 edge/stable 标签。发布过程使用独立渠道并发控制；取消测试构建不能取消正式发布。避免先写渠道成功标记后上传失败，也避免旧工作流晚完成覆盖新目标。

   补发旧 Release 或重跑旧提交也不能把渠道退回旧版本；先比较当前渠道revision/正式版本，再决定是否只发布该固定产物而不移动渠道。GitHub Release可以先出现“发布中”，但页面必须等镜像存在后才可安装。现工作流增加push/release后，不能直接使用仅workflow_dispatch才有值的inputs作为platform/version；为每种事件显式确定来源。
6. 初期两个渠道以 linux/amd64 为实际验收架构，和当前部署一致；不能默默恢复仅 amd64 的镜像覆盖已承诺的多架构渠道。若本阶段加入 arm64，必须同次完整发布并核验 manifest，各架构状态清晰，编译通过不冒充 ARM 运行验收。
7. 版本发现使用 GitHub Release + GHCR manifest/OCI 元数据即可优先采用；不为两渠道建设额外版本服务器。正式目标要对应仍存在的已发布正式 Release 和成功产物。发布元数据放可公开获取的现有产物位置；公共下载不要求每个站点配置仓库写 token。
8. 区分“最新源码”和“最新可安装版本”。纯文档提交没有新镜像是正常状态，不能永久显示等待构建；构建中/失败/明确跳过分别解释。平台架构不支持时不产生安装任务。
9. 删除旧 noise233 源与默认镜像对升级发现的参与；新版不再向 latest-mcp 发布。更新说明与引用只指向自有仓库。失败返回错误，不固定 hasUpdate=false。

验证：正式/测试不串渠道、Release 尚无镜像、构建失败、取消构建、纯文档跳过、API 限流、manifest 无当前架构、annotated tag、同提交两渠道、渠道落后/分叉、旧任务晚发布。发布脚本先本地模拟/测试仓库或明确测试标签验证，不为验证制造正式 Release。

完成：能返回真实可安装目标，当前部署可继续运行；本阶段不因为列表出现新版本就自动安装。

## 7. U2：任务与权限

1. 阅读全部旧升级调用及相关测试，构造 red：重复提交、SSE 断线不能启动第二次操作，非站长不能更新。
2. 在现有 services/models/controllers 边界实现最小持久化任务，接口薄、业务集中。保存确定目标 digest/revision/channel，不到实际执行时重新随意取 latest。
3. 明确单实例、单执行器起步，不做调度多个主机。claim、重复回报、状态转移和重启恢复有真实数据库测试。
4. 凭据创建/撤销、API 认证、响应脱敏、审计日志按现有模式实现。新凭据不能访问其他业务 API，普通管理员令牌不能冒充 executor。
5. 同步修改 version.update 的可委派定义、父能力关系和管理 UI；历史授权记录不能继续授予宿主更新，说明该变化，不清空无关管理员权限。
6. GET 旧升级流退役为明确不可用或纯查询，禁止 GET 触发；旧 POST 显式迁移至一次任务语义，不再 shell 执行。检查所有 fallback 和桌面调用后再删代码。

验证：访客、普通用户、委派管理员、站长、executor 五类角色；过期/撤销 token、任务 ID 枚举、跨任务回报、重复 POST、claim 响应丢失、数据库重启。日志不能含 token、宿主密码或完整敏感配置。

完成：无部署能力时仅能检查/配置，不能报已更新；客户端重复操作不会引起两次替换。

## 8. U3：外部执行器

**本阶段是项目施工，不是只给个人 NAS 写下载命令。** 交付可复用的项目脚本、配置示例、运维说明与真实隔离测试。只读使用 NAS 资料核实参数/依赖；不用当前业务实例证明未接 U4 的替换路径，不安装个人执行调度，不改第三方调度应用。

建议文件位置 `scripts/update/`，包含清楚命名的可执行脚本和无秘密示例配置。复用宿主 Docker CLI、Compose v2、curl、flock；JSON 解析用环境实际可用的标准能力（如 Python3），不要用 grep/sed 解析 JSON，也不为了少量字段新增后台服务。部署前检查依赖并给出安装提示，不静默修改宿主系统。

### 8.1 建议执行次序与阶段边界

先读路由、`internal/updates/`、模型、执行器认证及 U2 测试，列出真实请求/响应示例和状态转换；再用固定配置做依赖/部署核对、领取与回报、下载、恢复记录，最后在隔离环境验证 Docker/Compose 替换。U3 阶段曾保留产品路由 501 保护；该阶段已完成，当前以 U5 的 412 能力判断为准。内部函数与命令选项自行决定，不需要逐文件征求许可。

生产不能创建任务时，隔离测试使用临时数据库、真正的任务服务与真实认证/控制器：参照已有测试路由接入 `CreateUpdateTask`，或者由测试 fixture 经真实服务创建任务；不能把主库预填任务、加入生产危险开关、用假 HTTP 成功代替协调服务或临时开放真实站点安装。U3 的无业务数据样例只证明执行路径；最终真实数据路径必须在 U4 接入停机备份后验收。若当前宿主不具备独立 Docker 测试环境，先完成可运行交付并如实标注真实引擎验收未完成，不能把 mock 通过写成 U3 全部通过。

### 8.2 必须实现的行为

1. 由管理员固定配置：本地实例地址、执行器 token 文件、允许镜像仓库/变体、目标容器或 Compose 项目/服务、架构、状态/备份目录。配置文件权限受控，生产路径不能由待更新应用改写。
2. Docker 模式面向明确登记的固定部署，保留完整网络、设备、挂载、env/config、日志、restart 参数；不承诺无损克隆任意 docker inspect 配置。遇不支持参数拒绝并说明。
3. Compose 模式以管理员的 Compose 文件为配置真源，仅更新指定应用服务的镜像引用，保留项目名、卷和其他服务；使用 image 产物而非目标宿主源码 build，不执行 down -v，不重启独立数据库/MCP等无关服务。

   成功后的固定目标必须写入该部署后续启动会读取的受控image配置（例如专用环境文件），不只临时修改运行中的容器；否则管理员下次compose up可能意外切回旧版本。失败保留原配置记录，原子更新这一个字段，不重写用户整份compose。
4. 提供预构建 final-mcp 的单服务示例，不沿用会额外启动第二个 MCP 的旧示例。旧 compose 示例是否保留为本地开发用途需清晰标注，不能两份说明互相矛盾。
5. 每次调用先取宿主 flock，恢复/核对未结束本地记录，再去 claim；无任务 exit 0。下载完成后固定本地 image ID 和 remote digest，后续 docker run 不再次跟随移动标签。
6. 核对固定目标存在且对应登记数据布局，保存旧配置和镜像，执行 U4 才可停换；成功后不全局 prune，至少保留前一可恢复版本和必要备份。
7. 进度上报失败不终止已经进入不可中断阶段的安装，记录本地结果后重试；不能因为网络超时再执行一次安装。脚本退出码真实，调度工具显示成功必须意味着完成或空闲，而非吞掉失败。
8. 支持先核对部署、仅领取/报告、按固定部署执行这些实际需要的入口；无需为此设计通用插件框架。参数检查失败要在停旧应用前返回明确错误，不猜 Docker socket 权限、CPU 架构或数据路径。执行器运行超时/被终止后根据记录继续核对，不能简单删除锁文件视为“重新开始”。
9. 状态、备份和原配置存放在管理员控制目录，应用不能改写；并发锁只锁当前已登记部署。凭据文件仅执行用户可读，HTTP Authorization 通过受控文件/标准输入交给 curl，不放 URL、命令参数、shell trace 或 verbose 日志。日志保留任务和阶段，不输出原 env、挂载秘密或完整 HTTP 认证信息。
10. 从实际 registry 目标核对平台与拉取结果。区分多架构索引 digest、平台 manifest digest、本地 image ID；不能错误地要求三者字符串相等。记录对应关系，固定可验证的实际目标，不用移动标签或仅环境变量 `IMAGE_DIGEST` 自证成功。

### 8.3 U3 的交付与验收

测试：fake Docker/HTTP 可验证参数和错误分支，但不能替代真实独立 Docker 引擎上的容器替换。要验证应用停机后执行器继续、Compose 其他服务不变、重复启动脚本互斥、镜像架构错/磁盘不足、token 失效、网络中断。

进一步覆盖：claim 响应丢失后取回原任务、回报超时/409、正常凭据轮换与撤销的不同结果、记录存在时拒绝领取另一任务、记录与 instance_id 不一致、目标已启动但最终回报丢失、脚本被杀后只核对/补报不重复替换。真实测试用临时卷和独立端口，证明替换后 Compose 再次 up 仍保持目标版本，并保持另一服务的容器身份/挂载。

U3 完成时交付：项目脚本及无秘密配置、Docker/Compose 两种运行示例、独立任务测试入口/命令、日志与恢复说明、实际测试证据，以及 U4 要接入的停机/备份位置。例子必须能从领取任务运行到隔离容器结果确认，不只写函数空壳；尚未接入的正式备份只可在明确标注的隔离 fixture 中模拟，不能在产品脚本中用空函数报 backing_up 成功，更不能把样例成功当数据保护验收。文档说明初次配对如何获取 token、固定 instance_id、选择登记部署和检查权限，避免要求管理员自行猜 API。

**验收结论必须分开：** 本地测试是否通过、真实 Docker/Compose 样例是否通过、现有 NAS 是否接入。U3 不要求最后一项，也不能宣称真实数据自动更新已完成。固定部署配置可回顾、可复现，脚本不依赖开发电脑或应用进程存活；U4 前产品继续不可安装。

## 9. U4：一致备份和失败处理

默认采用清晰的停机备份顺序，避免为更新新造全站在线冻结框架：先拉取新镜像、检查空间 → 优雅停止旧应用（包括其内置后台 worker）→ 使用旧安装版本的备份能力完成一致归档和受保护配置备份 → 确認可用 → 替换并启动新应用。

镜像需要提供可独立调用的备份命令时，在既有 Go 代码上加最小 CLI 入口，复用 `backup.CreateArchive`；该模式不得启动服务/worker、执行普通启动迁移或应用待恢复包。用旧镜像运行同一工具访问相同数据布局，准确处理 WAL、外置 Blob、兼容媒体目录和配置秘密；连接策略须用测试证明。若不能复用，先解释真实阻碍，再调整实现，禁止直接复制活跃主库冒充一致备份。

首次启用自动更新的引导版本必须已经包含此工具；更老版本不能假装支持，走 U6 一次性引导。宿主能写备份位置，备份不要放在被归档目录内部，避免递归归档和磁盘填满。大附件备份时间计入停机预期；此阶段不为性能引入增量备份系统。

停机前明确目标是唯一数据写入者，检查并协调已有恢复/重启/同步任务。优雅退出超时或者不能证实 worker/其他写入者已停止，就不进入备份替换。旧容器保留为恢复材料时，处理其自动重启策略，避免 NAS/Docker 重启把旧实例拉起与新版同时写同一目录；只对登记目标记录/控制策略，结束后恢复应有配置，不全局修改 Docker。此风险必须通过实际中断/重启场景验证。

先写“即将启动新版”的记录再执行启动。Docker 启动命令返回错误不证明新版从未运行；结合实际容器与记录判断，无法证明时视为可能已经迁移/写入。回退旧运行配置和保留备份不等于已经允许恢复业务数据库。

失败规则：

| 阶段 | 处理 |
| --- | --- |
| 拉取/空间/身份检查失败 | 旧服务不动，任务失败 |
| 已停止旧服务、备份失败 | 未启动新版且数据未改变时可重启旧服务，报失败；不是降级 |
| 新容器未启动、原配置完整 | 证实未发生迁移/业务写入后可恢复旧运行实例 |
| 新版已启动或是否迁移不明 | 不自动恢复旧数据库，不盲目运行旧镜像；标 needs_attention，保留新旧镜像、备份及操作说明 |
| 新版健康/身份验证失败 | 不报成功；记录状态，按上述数据变化边界处理 |
| 成功后业务已写入 | 后续切旧版本不属于更新失败自动回退，禁止恢复旧备份吞掉新写入 |

只验证“容器 running”不够，需已有 health、同一 instance_id、受限 runtime 的完整 revision，以及宿主实际运行镜像与选定 digest/平台的对应关系。环境变量里的镜像声明只是辅助信息，不是独立证据。应用启动后可能有写入，不能宣传此时仍可无损自动恢复旧快照。独立测试必须实际走一次备份恢复，证明配置、笔记、附件及 SQLite 数据可读；真实数据恢复另外授权。

与已有备份/恢复/同步协调：若有未结束恢复或计划重启，拒绝启动更新；阻止更新与备份恢复竞争。复用已有锁/状态，先读全部调用方再修改，不能仅以 HTTP 路由检查假定后台任务已停。

补齐第 4.3.2 节人工结案路径，用真实失联/撤销场景验证能解除占位而不绕过认证或恢复旧库。之后在独立实例跑一轮完整“领取 → 停机备份 → 替换 → 身份核验 → 补报”及失败恢复，再决定是否接通产品安装处理器。不得只因脚本存在就把 501 切成可用；U5 的能力判断/用户提示未就绪时，现有站点仍不开放安装。

完成：下载失败无影响、停机备份失败可恢复旧运行、启动后失败不误恢复数据，人工恢复及任务结案都可执行；备份工具和引导条件有实际验证。

## 10. U5：后台界面

沿用现有 VersionSection 和后台样式，不重新设计整个后台。安装信息明确“已安装版本/提交、后续跟随渠道、执行器配置/最近连接”；维护操作固定两块：正式版、测试版。

站长首次配置路径要可操作：创建一次性显示的执行器 token、读取 instance_id、按 U3 指引写宿主配置、执行连接检查，再显示最近连接及是否具备安装条件。网页只管理受限凭据与任务，不要求填 NAS SSH 密码或给调度工具管理权限。两渠道共享同一个执行器、实例和活动任务，占用中同时禁用另一渠道的安装。

状态与文案覆盖：已最新、可更新、渠道落后、历史分叉/无法比较、尚无正式版、构建中、构建失败、源码变动无需构建、当前架构不支持、执行器未配置/离线、升级进行中、需要人工处理。

站长点击后确认目标和短暂停机，处理当前草稿；不能声称其他用户未提交草稿也被保护。普通读者可见“维护中/稍后重试”按最小现有机制实现，不制造用户无感零停机承诺。

POST 一次任务后轮询只读状态。重复点击禁用，刷新页面恢复未结束任务，SSE若保留只用于读事件。HTTP 中断时显示等待服务恢复，不自动 fallback 再次发起更新。成功必须源于执行器结果和新服务身份，不用单次 200、进度100或固定延时刷新当成功。

“重新打开页面”的服务端查询已在 U5 完成；以下保留原要求，不能只靠该浏览器 localStorage 里的任务 ID。U5 优先在已有只读接口按权限返回活动任务/最近必要结果；若确需独立查询接口，保持最小范围。非站长仍遵守 U2 的字段脱敏。页面清缓存、换浏览器后也能发现 ongoing/needs_attention，不能显示“可以再更新”。已成功但浏览器未收到结果也从服务端恢复，不自动再 POST。

渠道较旧时允许改变跟随偏好，明确“当前安装保持，等待该渠道追上”；不能给不可用的更新按钮。未配置执行器时可检查和阅读部署指引。进度只用真实阶段，不捏造百分比。

配置过但已失联、引导版本/脚本过旧、数据库或布局不支持分别说明；“凭据有效”和“宿主可执行”分开。需要人工处理时给任务 ID、宿主日志位置及按 U4 结案/恢复的指引；后台长期不可访问则说明通过 NAS 任务日志与 SSH 查看，不能承诺故障页面还在线。

浏览器验收：两渠道及失败空态、重复点击、关闭/重开、停机重连、权限、暗色与320/390/768/1440宽度、日志脱敏。更新前后长附件/普通草稿不被相关UI更改，原表格回归继续执行。

### 11.3 容器运行适配必须解决的问题

| 当前实现或约束 | 接入处理与验证 |
| --- | --- |
| `preflight()` 使用本地 UNIX Docker、`DockerRootDir` 的目录及剩余空间 | 接入真实宿主 Engine，保留来源/平台检查；实际目录视图及磁盘测量必须可核对。优先受控映射，确需代码调整时保留原宿主模式；不能测容器层的空间冒充宿主镜像盘。 |
| `data_protection_available()` 检查 Docker inspect 的 Mount Source 在执行侧存在 | Docker 创建容器时 Source 指宿主路径，不指 Dagu 内部别名。固定配置、env/Compose、业务 Source 及后续工具挂载的路径需正确对应；优先按宿主绝对路径映射，避免 helper 数据卷被错误用于业务实例。 |
| `check_writers()` 拒绝其他可写同一业务目录的容器 | 初始方案对 Dagu 的业务目录视图采用只读、且避开可写父目录。配置/token/状态/备份控制目录独立读写，并保留 owner/mode 校验。不得把 Dagu 可写映射整个存储盘后删除/跳过保护，也不能把“这是执行器”变成其他写入容器的免检名单。 |
| `check_writers()` 检查 `/proc`、宿主 PID、文件描述符 | 容器默认 PID/权限视图不足；按实测配置宿主 PID 视图及必要权限，并验证真实宿主写入进程和另一容器写入者可被发现。root 不自动证明能够读取所有进程 fd；无法证明检测有效则拒绝安装。不要默认 `privileged: true` 或屏蔽 PermissionError。 |
| 多入口及 Dagu 重试/超时 | Webhook、定时、手工调用共用原 flock/原子恢复记录。定时与长任务重叠由调度避免或识别“已运行”，不把所有非零退出吞成成功；失败恢复先读记录，不能用 Dagu 重试整个流程强制重装。 |
| 执行容器重建、NAS/Docker 重启 | state_dir、token 文件引用、image 文件和备份持久化且不属于待替换应用容器层。恢复要沿原任务阶段核验；不依赖 Dagu 运行记录替代执行器 active.json。旧业务容器仍保持 U4 的 restart 控制，防双写。 |
| 默认镜像、Host 网络与凭据传输 | 实查依赖、监听地址和端口冲突。独立任务容器里的 127.0.0.1 不自动指向 NAS；非回环应用连接继续使用 HTTPS 及证书验证，不关闭原校验。只给执行侧 Docker socket，应用只持有固定任务唤醒凭据。 |

优先把执行器直接放在 Dagu 的可复现运行环境中。若只能选择由 Dagu 启动专用执行容器，应先说明实测原因，再给一个固定任务的简单实现；不为本次引入通用执行框架。任务、凭据、日志和备份仍落在 NAS 持久卷，但日常管理在 Dagu 网页完成，不要求用户手工维护宿主脚本进程。

### 11.4 可选唤醒及 Dagu 任务约定

- 默认通过部署配置/私有配置文件提供固定触发 URL、凭据引用和有限超时，具体命名由实施者决定并写进示例。不增加通用 Webhook 编辑平台；如沿用后台设置，则写入仅固定 ID 1、读响应脱敏。应用无法到达 NAS 触发端时保持领取方案可用。
- Dagu 开启内置认证（当前官方配置 `DAGU_AUTH_MODE=builtin`），为一个固定更新任务配置 Webhook，触发 `POST /api/v1/webhooks/{fileName}` 并使用专用 Bearer token；按已安装版本核验接口。应用只有触发权限，不持 Dagu 管理登录、脚本编辑或任意任务运行凭据。传输走明确本机/内网部署边界，远程或不受信任网络使用 HTTPS，不关闭证书校验。用户已能打开网页不代表认证已完成，U6 实查。
- 应用先完成数据库任务事务，再发送有超时的固定请求。URL 仅由受信部署配置决定，允许明确配置的 NAS 私网目标，不给普通请求参数选择 URL；不跟随重定向、不把 token 写进 URL/日志/浏览器，不传 shell、宿主路径或待执行镜像参数。唤醒成功只说明请求被接受；执行器仍用另一份 executor token 领取并核对任务/目标。
- 创建后唤醒失败仍返回已保存的任务 ID，页面继续查询该任务，Dagu 定时补偿；不得返回“未创建”诱导重试。是否需要新增脱敏提示字段，先用真实断连场景判断，复用现有任务恢复能力。请求/响应丢失或同一活动任务重复提交均不创建第二条任务，重复唤醒也只使同一执行器检查领取。
- 定时先每分钟调用现有 `run`，空闲时完成真实 `check`/领取，存在记录先恢复。当前能力有效窗口 3 分钟，不能只部署一个被动 Webhook，否则空闲几分钟后更新按钮会失效。长更新期间不用另一任务并发检查旧实例或重新安装；结束后恢复正常检查。定时发现镜像变化不自动建任务。
- Dagu 任务应如实反映脚本退出状态，记录任务 ID/阶段及有限错误码；秘密保存在受控文件/密钥存储，网页任务定义和运行日志不放明文。超时按真实备份量与下载时间设置；显式 Stop、调度停止、容器重建均可能中断执行，要纳入恢复测试。
- 只读/低风险任务配置可在 Dagu 网页编辑；核心执行器按明确版本交付，升级时核对能力并保留记录。停用时同时处理 Webhook 与定时入口；存在未结任务先按 U4 处置，不能删记录/token 解除活动占位。Dagu 本身升级与 Echo Noise 更新分开，不自动给 Dagu 跟随 latest 重建。

### 11.5 U6 验收与交付边界
