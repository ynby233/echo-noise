# 云存储接入（R2/S3）

后台分为五个模块：**附件存储、云备份通道、数据备份、附件备份、服务器配置备份**。附件存储决定运行中的附件保存位置；云备份通道为三类备份提供独立的 R2/S3 目标，两套配置分别保存。配置通道、定时备份和发现云端历史都不会自动恢复数据；旧双向同步已停用。

## 云备份通道

云备份通道仅固定用户 ID 1 站长可查看和管理。备份含数据库、密码库或配置等敏感内容，应使用私有桶。

| 字段 | 填写方式 |
| --- | --- |
| 提供方 | R2（`r2`）或兼容 S3（`s3`） |
| Endpoint | 带协议的基础地址，不带 Bucket 或目录，如 `https://<account-id>.r2.cloudflarestorage.com` |
| Region | R2 通常为 `auto`；S3 填厂商实际区域 |
| Bucket | 单独填写桶名 |
| Access Key / Secret Key | 分别填写访问密钥 ID 与机密密钥；保存后以已配置状态表示，留空保持原值，清除需显式操作 |
| 路径风格 | 按厂商要求保存 `usePathStyle`；R2 页面选择逻辑开启此项 |
| 公共访问前缀 | 可留空；其 URL 路径部分参与对象 key 前缀，域名不能替代 Endpoint，也不要求桶公开 |

通道凭据需支持上传、读取、列举和按保留策略删除托管对象。云端托管 key 为 `noise-managed-backups/<kind>/<id>.zip`，再叠加配置的路径前缀；例如前缀路径 `note` 下的数据备份为 `note/noise-managed-backups/data/<id>.zip`。每条历史有独立 ID，不再覆盖单个 `backup.zip`。改变桶或前缀会改变后续历史发现范围。

## 三类备份与计划

三类备份分别创建、查看历史和设置计划，目标均可选 `local`（本地）、`cloud`（云端）、`both`（双方）。云端目标生成临时归档后上传，不代表长期保留本地副本。

| 类型 | 内容 | 默认容器本地历史目录 |
| --- | --- | --- |
| `data` | SQLite 主库 `database.db` 与独立密码库 `plain-passwords.db`，不包含附件文件 | `/app/data/backups/database` |
| `attachments` | 附件清单、所选范围的受管理文件及实际存在的兼容媒体目录 | `/app/data/backups/attachments` |
| `server-config` | 仅 `config.yaml`、`runtime.env` | `/app/data/backups/config` |

每类计划独立设置启用状态、每日 `HH:MM`、IANA 时区（如 `Asia/Shanghai`）、目标、范围及本地/云端保留数量。`keepLocal` 与 `keepCloud` 都必须为 **1..1000**，同类同端的手动、自动备份合计计数。新备份成功并持久记录可用副本后才清理超额历史；上传失败不会触发旧副本清理。清理失败会记录错误，不能只看新对象存在就认为整项操作无异常。

数据备份目前仅支持 SQLite，主库通过 `VACUUM INTO` 生成一致快照，独立密码库分别生成快照并校验配对。跨库没有同时锁定，并发改密码可能导致快照时间不同；归档中的警告需保留。不要复制运行中的主数据库文件来代替快照，也不要遗漏 WAL。PostgreSQL/MySQL 应采用数据库服务商或管理员验证过的备份恢复方案。

附件范围可选 `local`（本地）或 `all`（本地及受管理云端附件）；managed API 未指定范围时默认 `all`。`all` 会读取云对象写入归档，不能仅因数据库中存在对象引用就认为文件已经备份。正文中的任意外链不会被抓取，外部网站内容应另行保存。

服务器配置归档只收录文件白名单中的 `config.yaml`、`runtime.env`。环境文件仅接受变量白名单内的字面量赋值，拒绝命令替换和可执行 Shell 指令。恢复路径守卫校验数据库、密码库、附件路径，拒绝切换数据库类型或把配置指向另一份数据；路径遍历、符号链接和重叠恢复目标也受校验。外部挂载的密钥文件、Compose/容器编排、镜像和其他部署资料须另行保留；环境文件中的密钥路径不等于密钥内容已被备份。

## 新服务器发现历史与恢复

1. 在新服务器准备持久卷、当前数据库/密码库/附件路径和独立密钥挂载，再由站长配置同一云备份通道、Bucket 与前缀。
2. 打开所需类型的历史。历史查询会列举并发现通道内的托管 ZIP，无需先恢复旧数据库；发现失败时查看返回的 warnings，不把空列表直接当作云端没有备份。
3. 选择记录及 `local` 或 `cloud` 来源，或上传 ZIP 进行检查。发现对象只表示找到记录，恢复前仍须校验包、类型、完整性和警告。
4. 站长明确确认恢复。附件 `original` 模式使用**当前配置**的附件云存储并检查可用性；如果需要改为本地存储，必须显式选择 `local` 并再次确认本地迁移。云端不可用时不会静默回退。
5. 校验暂存成功返回 HTTP **202**、`pendingRestart: true`。这是等待重启，尚未应用；按部署方式重启，启动流程在数据库连接和后台任务启动前应用恢复，再核对健康状态、正文、附件与配置。保留失败信息与回退材料。

不存在按远端更新时间自动拉取恢复的流程。恢复始终需要人工确认，定时任务只创建备份。兼容旧 ZIP 仍可由站长上传；旧包的缺失组件及不完整迁移警告应按检查结果处理，不能把旧数据库包称为完整迁移备份。

## 权限与 API

受托管理员可按能力获授数据/附件的查看、创建、计划及历史操作，能力还受父权限约束。**整包下载和恢复全部仅限站长**；服务器配置类型的所有操作及云备份通道也仅限站长。授权创建或查看历史不会赋予整包下载权限。

以下路径均位于 `/api/admin/backups`，要求有效登录会话。`kind` 为 `data`、`attachments`、`server-config`；JSON 业务成功使用 `code: 1`。

| 方法与相对路径 | 请求与结果 |
| --- | --- |
| `GET /status` | 返回当前可见类型的计划、目录和待重启状态 |
| `PUT /plans/:kind` | JSON：`enabled`、`time`、`timezone`、`keepLocal`、`keepCloud`、`target`、`scope`；非附件 scope 为 `default` |
| `POST /:kind/create` | JSON：`target`、`scope`，创建一条手动备份记录 |
| `GET /:kind/history` | 刷新发现历史，返回 records、warnings、pendingRestart |
| `GET /:kind/history/:id/download?source=local` | 站长下载指定副本；source 可为 `local` 或 `cloud` |
| `POST /:kind/history/:id/restore` | 站长提交 `source`、`confirm: true`、`attachmentMode: "original"`；改为 `local` 时还需 `confirmLocalMigration: true` |
| `POST /inspect` | 站长以 multipart 字段 `file` 上传 ZIP 检查 |
| `POST /restore` | 站长上传并明确确认恢复；multipart 字段见下文 |

上传检查及恢复的文件上限为 2 GiB。`/restore` 使用 `file`、`confirm=true`、`attachmentMode=original`；本地迁移使用 `attachmentMode=local` 和 `confirmLocalMigration=true`。上传的旧 ZIP 也要求站长权限。

旧 `POST /api/backup/restore` 保留站长兼容上传入口，multipart 文件字段为 `database`，也必须提交 `confirm=true`。以下旧接口返回 HTTP **410 Gone**，应迁移到上述 managed API：

- `GET /api/backup/download`
- `POST /api/backup/storage/upload`、`/api/backup/storage/restore`（旧任意 URL 上传/恢复）
- `POST /api/backup/storage/presign/upload`、`/api/backup/storage/presign/download`
- `POST /api/backup/storage/sync-now`、`/api/backup/storage/sync-confirm`

本说明依据当前 managed API、typed 归档与存储实现，不代表已经完成生产 R2/S3 全流程验证。实现入口：`internal/controllers/managed_backup.go`、`internal/routers/managed_backup_routes.go`、`internal/syncmanager/managed.go`、`internal/syncmanager/managed_storage.go`、`internal/backup/typed.go`、`internal/backup/config_restore.go`、`internal/controllers/backup.go`。
