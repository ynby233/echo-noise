# R2 通知性能验证

日期：2026-09-08。基线提交：`556ebd3180a2ffeb0afa8e21c7dcdcdeb27992a4`。

## 结论

通知列表和未读数已从“全量构造页面响应并逐条解析查看者权限”改为三个阶段：轻量资格与目标状态判定、计数及选页、只对最终页 Hydrate。4,000 条通知的列表和未读数在相同 Windows 机器、相同合成数据库上均降低超过 75%；双并发降低超过 85%。测试期间没有接口失败，返回大小与优化前一致。

这些数字用于比较本次改动前后，不是 NAS 容量承诺，也没有写成 CI 的绝对耗时门槛。

## 测量方法

- 数据来自发布验收使用的合成数据库，不包含 NAS 生产数据。
- HTTP 测量使用当前服务的 `/api/notifications?page=1&pageSize=20` 和 `/api/notifications/unread-count`。
- 每个单并发场景连续请求 10 次；双并发由两个执行单元各请求 10 次，共 20 次。
- 0、100、4,000、20,000 条数据分别位于隔离数据库副本；每轮启动独立服务，结束后停止该服务。
- SQL 次数、读取行数和 Go 分配量由一次性诊断回调测量；诊断代码未保留在产品或测试套件中。

## 4,000 条前后对比

| 接口 | 并发 | 优化前 p50 | 优化后 p50 | 降低 |
| --- | ---: | ---: | ---: | ---: |
| 通知列表 | 1 | 187.1 ms | 45.7 ms | 75.6% |
| 未读数 | 1 | 186.5 ms | 32.2 ms | 82.7% |
| 通知列表 | 2 | 505.7 ms | 63.1 ms | 87.5% |
| 未读数 | 2 | 520.7 ms | 58.2 ms | 88.8% |

优化前一次全量通知构造读取 4,000 条通知时执行 16,005 次查询、累计读取约 24,002 行、分配约 86.2 MB。优化后实际列表第一页执行 22 次查询、累计读取约 8,064 行、分配约 13.9 MB；未读数执行 18 次查询、累计读取约 8,002 行、分配约 13.5 MB。读取行数仍包含轻量资格判断需要的通知、笔记状态和有效点赞，不包含未读接口不需要的评论及页面正文构造。

`EXPLAIN QUERY PLAN` 在改动前使用单列收件人索引并显示 `USE TEMP B-TREE FOR ORDER BY`。增加 `(recipient_user_id, created_at, id)` 复合索引并完成迁移后，计划直接使用 `idx_user_notifications_recipient_created_id`，不再使用临时排序 B-tree。

## 规模结果

| 通知数 | 列表 p50，并发 1 | 未读 p50，并发 1 | 列表 p50，并发 2 | 未读 p50，并发 2 |
| ---: | ---: | ---: | ---: | ---: |
| 0 | 15.1 ms | 15.8 ms | 15.7 ms | 15.7 ms |
| 100 | 15.5 ms | 15.6 ms | 4.9 ms | 3.5 ms |
| 4,000 | 45.7 ms | 32.2 ms | 63.1 ms | 58.2 ms |
| 20,000 | 94.6 ms | 87.3 ms | 155.1 ms | 143.1 ms |

100 条双并发结果受 Windows 本地调度与缓存影响，低于单并发；它只证明该轮没有退化或失败，不用于推断并发吞吐。20,000 条场景的所有请求均成功，但仍需把真实 NAS 硬件、磁盘和并发条件作为独立验证边界。

## 语义回归范围

HTTP 回归测试覆盖：点赞、评论、回复、留言、三类账号通知、内容删除通知；已读与未读；撤回点赞过滤；目标删除、私密或不可见时的占位；删除快照；相同时间按 `created_at DESC, id DESC` 排序；过滤项跨分页边界时的 `total` 与满页；第二身份；最终页 Hydrate；未读数不构造页面评论或逐条解析查看者权限。
